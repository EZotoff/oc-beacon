## 1. 问题陈述

### 1.1 #424 步组内容后台解析预取池(L0)（backlog.md:198-200）

- **用户提案原文**：「守护线程池(如2线程)后台预取 Markdown 解析——Compose 组合/测量是主线程铁律不可搬,但解析(最重CPU段)可并行;卡片可见即预取解析模型,ε 组合直接命中缓存」（backlog.md:199）。
- **依赖声明**：「与 CardExpandReveal PREWARM 衔接(解析预热→组合预热两层)」（backlog.md:200）。
- **用户可感知症状**（立卡时语境）：大内容折叠卡首次展开等待 3~5s（#429 主诉族，含解析 Loading 首帧）；预热命中后 265ms vs 暖进程未预热 ~2.4s vs 真冷 3~5s（docs/research/2026-09-28-issue429-research.md:21-23）。

### 1.2 #425 预热错峰:滚动停止后多卡同帧预热风暴（backlog.md:194-196）

- **症状**：实测 Skipped 53 帧（~880ms 空闲停顿）——多张折叠卡同一空闲窗并发 ε 组合（backlog.md:195）。
- **卡内既定方案**：「PreRenderCoordinator 队列化,一卡一窗串行预热」（backlog.md:196）。

### 1.3 命名澄清：#424 的「L0」与 #429 的「L0-L3」是两套编号

#429 卡片的交付分层是「L0 风暴收敛→L1 表格行组切片→L2 首窗即时→L3 完全体渐进」（backlog.md:127，spec 2026-09-23-progressive-card-expand-design），其 L0 指**交付阶段**；#424 标题的「(L0)」指**渲染管线层级**（解析层=第 0 层，组合/测量不可后台是硬边界，其下无可挪移阶段）。两处 L0 语义无关，检索时须按卡片上下文区分。

### 1.4 同族关系

两卡是同一资源调度问题的两层：**#424 = 后台线程层（解析预取的并行度与覆盖面），#425 = 主线程层（组合预热的空闲窗调度）**。#427 卡片明言「收编 #424/#425 动机」（backlog.md:188），其 P1-P3（切片+账本+窗口化）落地后留档「P3b 预热错峰未做」（backlog.md:192）。

### 3.1 解析预取三件套（#424 设想的「池」现状）

```
视口/世界变化（ChatMessageList.kt:1058-1090 桥接）
  → RenderSupplyCoordinator.onViewportChanged/onWorldArrived
```

## 4. 根因分析（含置信度）

**R-A（#425 主根因）预热无全局调度，同帧齐发**——置信度：**高**
每卡独立 LaunchedEffect 共用同一 1200ms 静止时钟，滚动停止后同帧并发 ε 组合；实测 Skipped 53 帧 ~880ms（journal:312-314）+「集末风暴期多卡 PRD-warm 并发」（journal:336-339）。让位环只等 episode（:1041-1047），卡间无互斥。**结构性缺陷至今零改动**（自批次十三起 prewarm effect 形态未变）。

**R-B（#425 次根因）单卡预热成本无帧预算上限**——置信度：**高**
warmup+settle 在一帧内组合整卡内容：怪物片 2.5s 主线程长块、42 帧掉帧（journal:488）。错峰（串行）只消除「并发叠加」，不消除「单卡长块」——20k px 级卡片即便串行仍会产生一次长帧（journal:313-314 已知边界同款）。资格门曾试图挡此案（fac75665），现成死参数。

**R-C（#424 真实残余根因）synthetic 段预解析盲区**——置信度：**高（存在性）/ 中（用户可感度）**
双端排除（RenderSupplyCoordinator.kt:329；MessageCardAssistant.kt:338、:813）+ 组合期派生（StepGroupSlicing.kt:94-96）使切片段永远拿不到 registry 预热；2200 预算 > 2048 异步阈值使多数段带 Loading 首帧。**待验证**：DEBUG 日志统计窗口片进窗首帧 Loading 占比与 hitch 贡献（复跑 issue431 批次十五脚本）。

**R-D（#424 提案过时）「守护线程池」与现状重复 + 主对象已退役**——置信度：**高**
解析已在 Default 后台（RenderReadiness.kt:121-127），专用 2 线程池的增量仅剩「限流防挤占」（现无并发上限，一轮窗口扫描可打数十个 part 到全核 Default）与「取消语义」（parseScope 生命周期随列表，无逐条取消）；而提案的主链路「步组卡可见→预取→ε 组合命中缓存」已被 #430 裁决退役（7d5cd5fc，MessageCardAssistant.kt:1305-1311）。按字面实施=重复建设+服务已不存在的场景。

**R-E（两卡共同结构约束）组合/测量主线程铁律**——置信度：**高**
官方无后台组合 API（2026-09-24 可行性 Q1 源码级确证 :17、:24）；「预热」本质是主线程空闲期成本挪移，错峰=在「预热收益（首开 80ms vs 450ms，journal:303）」与「空闲窗完整性」之间做调度，不存在免费午餐。

**小结**：#425 的根因（R-A/R-B）完整存续，只是暴露面从「步组怪物卡+多卡并发」收窄为「剩余折叠卡族多卡并发」；#424 的字面根因（缺后台解析池）不成立（R-D），其意图层的真实缺口是 R-C（synthetic 盲区）——恰为 issue431 方案一第 3 条的既定范围。

## 5. 修复方案空间

### 方案 A「队列化 + 盲区补丁」（保守，推荐）
